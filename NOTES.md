  - TTFT is the latency the user actually feels; total time matters less once text is flowing.

### 2026-10-09 — 1.2 Multi-turn chat CLI (`01-fundamentals/chat-cli`)

- **What I did:**
  - Built a terminal chat in TS and Python: a loop that keeps a `history` array, sends it on every turn with streaming, and appends the assistant reply.
  - Commands handled locally (never sent to the model): `/history`, `/reset` (alias `/clear`), `/exit`; any other `/...` is rejected as unknown.
  - Optional sliding window with `MAX_HISTORY=N`: only the last N messages are sent.
  - Local token estimate with `o200k_base` (`js-tiktoken` / `tiktoken`) next to the real `usage` from the API.
  - One JSON log per run in `sessions/`: current `history`, `lastSent` and an append-only `transcript` with time, tokens and cost per turn.
  - Moved the reusable code to `shared/` (pnpm workspace `@journey/shared` + uv workspace `journey_shared`): config and prices, streaming call, cost, token estimate, metrics line, session log.
- **What I learned:**
  - The model has no memory: the chat's "memory" is the array I resend. Input tokens therefore grow with the conversation, and every turn pays again for everything before it.
  - The model can claim things it never did: when I typed `/clear` before it was a command, it went to the model as a normal message and the model replied "Conversation cleared." while nothing was cleared.
  - What I send (`history`) and what I log (`transcript`) are different things: a reset must empty the first and only be recorded in the second.
  - `toSend = history` shares the reference (in JS and Python); pushing the reply later also changed what I had logged as "sent". Always copy: `[...history]` / `list(history)`.
  - Reasoning tokens depend on the question: open questions used 43–86 reasoning tokens, short follow-ups used 0.
- **Experiments:**

- **Conclusion:** the context window is a budget I manage, not memory the model has. Sending everything is simple, but cost and latency grow every turn; a window caps the cost but forgets, and it can cut a turn in half. The real question is _what_ to keep (whole turns, a summary of old messages, key facts like the user's name): that is context engineering.

### 2026-10-11 — 1.3 Structured extraction (`01-fundamentals/job-extraction`)

- **What I did:**
  - Downloaded 30 real AI Engineer job posts from public ATS APIs.
  - Extracted `seniority` (enum), `remote` (`boolean | null`), `stack` and `required_skills` from each post with three implementations, all writing the same JSON shape to `data/extractions/`:
    - TS + OpenAI SDK: `responses.parse` + `zodTextFormat` → `openai-ts.json`
    - TS + Vercel AI SDK: `generateText` + `Output.object` → `ai-sdk.json`
    - Python + OpenAI SDK: `responses.parse(text_format=...)` + Pydantic → `openai-py.json`
  - Error handling: one retry telling the model why its previous answer was rejected; fatal errors (401/403/no credit) stop the run; a post that fails twice is saved with `extracted: null` and the error; results are saved after every post; `LIMIT=N` to test cheaply.
  - In TS, `common.ts` holds the schema, instructions and retry loop; each script only implements one attempt (`extractOnce`). Python is a single file because there is only one script.
- **What I learned:**
  - Structured outputs turn free text into data my code can use. The LLM is only for what is buried in the text: title, company and URL were already in the file header, so I don't pay the model to extract them.
  - The `index.json` is the catalog (which file to read), not the input: the input is the post text.
  - OpenAI strict mode: every field is required, so "may be missing" is `.nullable()` in Zod / `bool | None` without default in Pydantic, never `.optional()`.
  - The schema rules are the real work: what counts as "mid" vs "senior", what `remote: null` means, `stack` vs `required_skills`. Without explicit rules the model fills the gaps by inferring.
  - Native SDK vs AI SDK:

|                                | OpenAI SDK                                                             | Vercel AI SDK                                           |
| ------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------------- |
| Schema                         | `text: { format: zodTextFormat(schema, name) }`                        | `output: Output.object({ schema })`                     |
| Result                         | `response.output_parsed`                                               | `output`                                                |
| Invalid JSON / schema mismatch | throws `ZodError` (TS) / `ValidationError` (Py)                        | throws `NoObjectGeneratedError` (detail in `err.cause`) |
| Refusal / truncated answer     | does not throw: I check `refusal` and `status === "incomplete"` myself | becomes an error                                        |
| Tokens of a failed attempt     | lost when validation fails                                             | available in `err.usage`                                |
| HTTP status on errors          | `err.status` (TS) / `err.status_code` (Py)                             | `err.statusCode`                                        |

### 2026-10-13 — 1.4 Tool loop (`01-fundamentals/tool-loop`)

- **What I did:**
  - Built a one-question terminal assistant (`pnpm ask "..."` / `uv run ask.py "..."`) that answers from the 1.3 data through four deterministic tools, with no LLM inside them:
    - `search_jobs({ seniority, remote, technologies, company })`: every filter nullable, `technologies` must all match, up to 10 jobs plus `total`.
    - `get_job_details({ id })`: the full extraction, URL and the first 1,500 characters of the post.
    - `count_technologies({ seniority, top_n })`: the most mentioned technologies, each counted once per job.
    - `compare_jobs({ ids })` (bonus): the jobs side by side plus the technologies they share.
  - Tool schemas written by hand as JSON Schema with `strict: true`, shared by the TS versions (`tools.ts`).
  - The loop by hand with the OpenAI SDK in TS (`ask.ts`) and Python (`ask.py`). It runs every `function_call` in a response, sends back the whole `response.output` plus one `function_call_output` per `call_id`, and stops at a response with no calls or after `MAX_STEPS` (5) model calls, printing `[step limit reached]`.
  - The same assistant with the Vercel AI SDK (`ask-ai-sdk.ts`): `tool({ description, inputSchema: jsonSchema(...), execute, strict: true })`, `generateText` with `stopWhen: [isStepCount(5)]`, and `onStepEnd` for the trace.
  - Tool errors never throw: an unknown id returns `{ "error": "job 99 not found" }`, invalid JSON arguments return an error the same way.
  - One JSON trace per run with `SessionLog` (`trace.ts`): the question, every step (tool calls, arguments, outputs, tokens, latency), the answer, and total tokens and cost.
  - Ran the 8 test questions in the three versions (24 runs, USD 0.0085 in total).
- **What I learned:**
  - The model never runs anything. It returns `function_call` items (a name, a JSON string of arguments and a `call_id`) and stops. My code runs the function, answers with a `function_call_output` carrying the same `call_id`, and calls the model again with the whole history.
  - The model decides when it's done: a response without function calls is the answer. Nothing else guarantees the loop ends, so the step limit is mandatory.
  - The whole `response.output` goes back into the input, not only the calls: reasoning items have to travel with the calls they belong to.
  - Strict mode again: every parameter is required, so optional filters are nullable (`"type": ["boolean", "null"]`), the same trap as 1.3.
  - Tool errors are data for the model, not exceptions for my code: "job 99 not found" came back as a normal answer in all three versions.
  - In the AI SDK, `@ai-sdk/openai` sends `strict: false` unless the tool sets `strict: true`.
  - The first request had exactly the same input tokens in the three versions for every question: same instructions, same hand-written schemas, same request. The library changes the code, not what the model sees.
  - The model chooses the strategy, and it's not stable: with the same first step, one run fetched the first job and another fetched all six. Parallel calls appeared when the model decided, not when the question needed them.
  - OpenAI SDK vs AI SDK for tools:

|                            | OpenAI SDK (by hand)                                                        | Vercel AI SDK                                                                |
| -------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Define a tool              | `{ type: "function", name, description, parameters, strict: true }`         | `tool({ description, inputSchema: jsonSchema(...), execute, strict: true })` |
| Run it                     | look up `call.name` in my tool map                                          | the SDK calls `execute`                                                      |
| Arguments                  | a JSON string: `JSON.parse` myself, `{ error }` if it fails                 | parsed by the SDK                                                            |
| The loop                   | `while` + push `response.output` and each `function_call_output` to `input` | `stopWhen: [isStepCount(5)]`                                                 |
| Several calls per response | map over the `function_call` items, one output per `call_id`                | automatic                                                                    |
| Step limit hit             | my own counter: the last response still has calls                           | `finishReason === "tool-calls"`                                              |
| Usage and time per step    | each `response.usage` + my own timer                                        | `onStepEnd(step)`: `step.usage`, `step.performance.responseTimeMs`           |

- **Conclusion:** the tool loop is small and not magic: call the model, run what it asks for, send back the results with their `call_id`, repeat until it stops asking or I stop it. The framework hides that loop but sends exactly the same request, and in my code it saved only 11 lines because adapting its steps to my trace costs almost as much as the loop. What decides cost and quality is not the library: the tool definitions are ~75% of every first request, a vague question can turn into 11 tool calls, and the model's strategy changes between runs. The descriptions and instructions are the real prompt of a tool-using assistant, and they need evals like any other prompt.
